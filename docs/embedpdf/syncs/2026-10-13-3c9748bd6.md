## Upstream changes outside the conflicts

- **Right-to-left `/ActualText`, again (`58d357aac`, `17cf94b52`).** Upstream now reverses an RTL
  `/ActualText` run in `ProcessTransformedTextObjects()` when its glyphs are RTL or it follows RTL
  text, and reverted S6's "mixed-direction line" change. That fixes literal RTL text followed by
  `/ActualText`, but a run that *starts* its RTL segment is still passed forward by
  `CloseTempLine()`, so reversing it first turned it back to front: exactly what Acrobat writes
  around each shaped Arabic or Hebrew run (`EPDFAnnotEmbedderTest.RichTextRtlRunCarriesActualTextAndExtracts`
  failed). Upstream's fixture covers Latin glyphs, so its test missed it. Our fix (bug-fix,
  tagged): reverse only after literal RTL text, found by looking back past spaces to the last
  character with a strong direction. Upstream's `ActualTextRtl` and `Arabic` tests still pass.
- **Content-stream writer moved to `core/fxcrt/stream_write_utils.h` (`ac60fa3da`).**
- **API changes in our tests:** `JpegModule::CreateDecoder()` takes `prefer_bgr_output`
  (`32d5e1d51`); `CompareBitmapWithFuzzyExpectationSuffix()` became `kFuzzyDiffOptions`
  (`a4f9c3c5d`).
- **New global:** `g_isolate_per_document` (`49026973e`, library config version 7). Library
  start-up and shutdown run on every worker thread (per-thread-init), and shutdown writes it,
  so it is `EPDF_TLS` now (tagged), on the allowlist as thread-local.
- **XFA per-document heaps and isolates** (`88c60350e`, `9bd9ac2ea`, `d793a0ddc`): not built.
- **New APIs:** `FPDFAttachment_GetAFRelationship()`, `FPDFPageObj_GetRenderedFillPattern()`,
  `FPDFPageObj_GetRenderedStrokePattern()`, `FPDF_StructElement_GetRawType()`.
- **Windows SDK:** the same `build/` revision as S7, so S7's SDK fix is carried here too.
