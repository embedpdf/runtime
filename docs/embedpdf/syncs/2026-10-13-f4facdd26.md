## Upstream changes outside the conflicts

- **Right-to-left text extraction (`2f7a54a92`, `17c6d8dae`, `f4facdd26`).** Upstream now keeps
  `/ActualText` in logical order when it closes a right-to-left line, gives those characters
  their own type, `kActualText` (they were `kPiece`), and stops reversing whole mixed-direction
  lines. Two follow-ups in our code:
  - our `bug-fix` block in `ProcessMarkedContent()` appended RTL `/ActualText` in visual order
    because the line closer used to reverse it. With upstream's fix both applied, and
    `EPDFAnnotEmbedderTest.RichTextRtlRunCarriesActualTextAndExtracts` extracted the Arabic run
    backwards. Upstream fixed the same bug, so ours is dropped (rule bug-fix);
  - `EPDFText_GetCharGeometry()` flags `kPiece` characters as synthesized. `/ActualText`
    characters are `kActualText` now and would have lost the flag (the engine would treat them as
    real glyphs); the check names both. `FPDFTextEmbedderTest.Bug384770169` guards it.
- **JPEGs decode at a reduced size (`5cebac774`).** A JPEG drawn small decodes at 1/2, 1/4 or 1/8
  of its size, through the same "resolution levels to skip" as JPX. Our decoded-image store kept
  only JPX decodes per levels, so it handed a 1/8 bitmap to a later full-size draw, or a full
  bitmap where a new decode would be reduced: renders no longer matched new decodes. The store now
  keys JPX and DCT decodes by levels (`CPDF_DIB::SkipsResolutionLevels()`, renamed from
  `IsJpxImage()`; the store's `jpx_levels` names became `levels_skipped`). Guard: upstream's
  `jpeg_reduced_size.pdf` added to `EPDFViewEmbedderTest.DecodedImageStoreRendersAsNewDecodes`
  at widths going both ways; it failed before the fix. A JPEG whose size isn't a multiple of its
  block size still decodes in full, but is kept per levels too: fewer hits, same pixels.
- **Enums renamed into `pdfium::unicode` (`510ad85d9`)**: `FX_BIDICLASS` → `BidiClass`,
  `FX_BREAKPROPERTY` → `BreakProperty`, `FX_CHARTYPE` → `CharType`. Ported in our rich-text layout
  and our moved line-break table.
- **Smaller API changes ported:** `CFX_Face::GetGlyphBBox()` takes the glyph index (our drawn
  bounds); `CPVT_VariableText::Alignment` (see the generator section).
- **Attachments.** `FPDFAttachment_SetStringValue()` stores text strings (`daa1a5da6`), and the
  new `FPDFAttachment_Get/SetDescription()` (`dae75842f`) read and write `/Desc`, as our
  `EPDFAttachment_Get/SetDescription()` already do. Ours differ in one way: an empty description
  removes `/Desc`. Both are kept for now (see Ledger changes proposed).
- **Flatten rejects XFA-only pages (`eb68153d4`).**
- **Text direction for form fields (`dd0c5caed`, `a4a2d6706`)**: `FORM_Get/SetTextDirection()`,
  for the form-fill environment, which the engine doesn't use.
- **`<windows.h>` in `cfx_renderdevice.h`, taken early from upstream's `3abda657c` (Aug 10).** S5's
  CI rerun showed win32-x64 failing to compile (`unknown type name 'HDC'`): upstream moved the
  Windows device into `cfx_renderdevice.h` (`fc790866b`, in S5) without its include. Its first
  run had died in the dependency fetch (HTTP 503), so S5 merged with it. Tagged bug-fix; S7
  brings the same lines, and then ours goes.
- **Skia moved `src/base/` into `src/core/`** (roll `d94c34e6e`); our `redaction_pathops` source
  list follows.
