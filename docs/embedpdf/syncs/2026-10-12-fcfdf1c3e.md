## Upstream's font subsetter in our fork

- **Full saves.** Upstream subsets in `WriteNewObjs()`. Our full save never runs it, so
  `FPDF_SUBSET_NEW_FONTS` did nothing there (upstream's two-font test wrote 258,660 bytes for
  ~12,000). `WriteFullDocument()` now builds the same overrides and writes them in place of the
  originals. Incremental saves keep going through `WriteNewObjs()`.
- **CID-keyed CFF fonts.** `FPDFText_LoadFont()` embeds an OpenType/CFF font as a
  `CIDFontType2` in `FontFile2`, and the text holds glyph indices. When subsetting, upstream turns
  it into a `CIDFontType0` with `FontFile3 /OpenType`. For a CID-keyed CFF (every Noto CJK font),
  a `CIDFontType0` selects glyphs by CID through the CFF charset (ISO 32000-2 9.7.4.2), and our
  reader does that (rule fonts). So the subset text drew nothing: in our build, and in any reader
  that follows the spec. PDFium upstream still draws it because it reads CIDs as glyph indices. We
  keep such a font as the `CIDFontType2` in `FontFile2` it was embedded as, with the subset
  program (tagged `EmbedPDF(fonts)` in `cpdf_fontsubsetter.{h,cpp}`). Name-keyed CFF fonts are
  converted as upstream does. Worth reporting upstream.
- **Layers.** The subsetter parses every page through `GetMutablePageDictionary()`. On a layer
  that is the copy-up door, which copies only on a write, and nothing writes. A subsetting save of
  a layer subsets and leaves the layer as it was (new test below).
- Neither the engine nor the viewer passes `FPDF_SUBSET_NEW_FONTS`. A subsetting save parses
  every page and fills the document's caches; it looks only at page content (not form XObjects or
  appearance streams), as upstream's does.
- Size: our build already linked HarfBuzz's subsetter (rich-text fonts); `__text` grew by 8 KB
  on darwin-arm64.

## Ledger changes proposed

- **save-traversal**: add to Rule: "A full save applies upstream's font-subset overrides
  (`FPDF_SUBSET_NEW_FONTS`) itself, to the objects `NewObjectNumbers()` lists." Guarded by:
  `EPDFSaveEmbedderTest.FullSaveSubsetsNewFonts`. When upstream touches this: "Whatever
  upstream adds to `WriteNewObjs()` that changes what an object is written as must reach
  `WriteFullDocument()` too."
- **fonts**: add to Rule: "The font subsetter keeps a CID-keyed CFF font a `CIDFontType2` in
  `FontFile2`; upstream converts it to a `CIDFontType0`, which selects glyphs by CID." Where:
  `cpdf_fontsubsetter.{h,cpp}`. Guarded by: `EPDFSaveEmbedderTest.FullSaveSubsetsNewFonts`.
- **fonts**, open issue (no code; nothing passes `FPDF_SUBSET_NEW_FONTS` today): the subsetter
  collects glyphs only from text objects at the top level of page content. It never sees text in
  form XObjects (flattened annotations included), annotation appearance streams, form field
  appearances or the form's `/DR`. A new font used only there is not subset, which is safe. A
  new font shared between page text and one of those is subset to the page's glyphs, so the
  annotation or field loses the others, and a field can't draw characters typed later. Our font
  registry shares one font object across page text, FreeText and fields, so this case is real
  for us. Not tested yet. Before the engine or viewer passes the flag: skip any new font that an
  annotation or field appearance or `/DR` references, collect glyphs from form XObjects too, and
  add a test for the shared case. Proposed When-upstream-touches-this line: "A change to how the
  subsetter collects glyphs: check fonts shared with annotations and form fields."
